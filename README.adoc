= WildFly A2A Feature-Pack

WARNING: This is an unsupported experimental POC implementation. Use with caution.

A WildFly feature-pack implementing the open-standard Agent2Agent (A2A) Protocol to enable universal interoperability and seamless collaboration between AI agents across diverse frameworks and vendors.

== Building

Build the A2A feature-pack:

[source,bash]
----
git clone https://github.com/rhusar/wildfly-a2a-feature-pack.git
cd wildfly-a2a-feature-pack
./mvnw clean install -DskipTests
----

== Provisioning with Maven

Use the `wildfly-maven-plugin` to provision WildFly with the A2A feature-pack.

=== A2A Server with All Transports (JSON-RPC, gRPC, REST)

For gRPC support, include the https://github.com/wildfly-extras/wildfly-grpc-feature-pack[wildfly-grpc-feature-pack]:

[source,xml]
----
<plugin>
    <groupId>org.wildfly.plugins</groupId>
    <artifactId>wildfly-maven-plugin</artifactId>
    <version>6.0.0.Final</version>
    <configuration>
        <feature-packs>
            <feature-pack>
                <groupId>org.wildfly</groupId>
                <artifactId>wildfly-galleon-pack</artifactId>
                <version>40.0.0.Final</version>
            </feature-pack>
            <feature-pack>
                <groupId>org.wildfly.grpc</groupId>
                <artifactId>wildfly-grpc-feature-pack</artifactId>
                <version>0.2.0.Final</version>
            </feature-pack>
            <feature-pack>
                <groupId>org.wildfly.a2a</groupId>
                <artifactId>wildfly-a2a-feature-pack</artifactId>
                <version>0.0.1.Alpha1-SNAPSHOT</version>
            </feature-pack>
        </feature-packs>
        <layers>
            <layer>cloud-server</layer>
            <layer>a2a-server-jsonrpc</layer>
            <layer>a2a-server-grpc</layer>
            <layer>a2a-server-http-json</layer>
            <layer>grpc</layer>
        </layers>
        <galleon-options>
            <jboss-fork-embedded>true</jboss-fork-embedded>
            <stability-level>experimental</stability-level>
        </galleon-options>
    </configuration>
    <executions>
        <execution>
            <goals>
                <goal>package</goal>
            </goals>
        </execution>
    </executions>
</plugin>
----

== Provisioning with WildFly Glow

The layers define https://github.com/wildfly/wildfly-glow[WildFly Glow] rules, so Glow can infer the
layer set from a deployment scan instead of a manually configured `<layers>` list. The base `a2a` layer is
discovered from A2A SDK usage in the deployment, and the client transport layers from the transport
class the application uses.

Glow takes feature-packs to scan against from a Galleon provisioning file, not from a command
line coordinate, so start with a `feature-packs.xml` listing both WildFly and this feature-pack:

[source,xml]
----
<installation xmlns="urn:jboss:galleon:provisioning:4.0">
    <feature-pack location="org.wildfly:wildfly-galleon-pack:41.0.0.Final"/>
    <feature-pack location="org.wildfly.a2a:wildfly-a2a-feature-pack:0.0.1.Alpha1-SNAPSHOT"/>
</installation>
----

[source,bash]
----
wildfly-glow scan my-a2a-app.war \
    --input-feature-packs-file=feature-packs.xml \
    --add-ons=a2a-server-jsonrpc \
    --package-stability-level=experimental \
    --config-stability-level=experimental \
    --provision=SERVER
----

Fow now, the stability options are required because all A2A layers are `experimental`.

=== Choosing Server Transport with Glow

A deployment that drives A2A purely through the SDK and CDI - an `AgentExecutor` plus a
`@PublicAgentCard` producer - carries no information for which _server_ transport to provision.
The three server layers are therefore offered as add-ons of
the `a2a-server` family (namely `a2a-server-jsonrpc`, `a2a-server-grpc`, `a2a-server-http-json`), selected
with `--add-ons`. The client layers form the `a2a-client` family and are additionally auto-detected
from the transport class the application uses.

A deployment that does reference the Jakarta EE implementation classes directly - for example a
JAX-RS resource that extends or calls `org.wildfly.a2a.jakarta.jsonrpc.A2AServerResource` - is
matched by that server layer's own class rule, and the layer is discovered without `--add-ons`.

`a2a-server-grpc` is not discoverable this way. It is usable only together with the
https://github.com/wildfly-extras/wildfly-grpc-feature-pack[gRPC feature-pack] and its `grpc` layer,
which no A2A layer can depend on because the feature-pack is optional. Were the layer auto-selected,
Glow would provision a server that resolves and boots but has no gRPC endpoint. Provision it
explicitly, alongside the gRPC feature-pack and the `grpc` layer.

== Layers

The feature-pack provides the following Galleon layers:

|===
|Layer |Description

|`a2a` |Base layer with A2A subsystem
|`a2a-client-jsonrpc` |A2A client with JSON-RPC 2.0 over HTTP transport
|`a2a-client-grpc` |A2A client with gRPC binary protocol transport
|`a2a-client-http-json` |A2A client with RESTful HTTP/JSON transport
|`a2a-server-jsonrpc` |A2A server with JSON-RPC 2.0 over HTTP transport
|`a2a-server-grpc` |A2A server with gRPC binary protocol transport
|`a2a-server-http-json` |A2A server with RESTful HTTP/JSON transport
|===

Server layers include both the A2A SDK transport module and the Jakarta EE implementation.
Client layers include only the SDK transport module.


== Running Integration Tests

Based on https://github.com/wildfly-extras/a2a-jakarta[a2a-jakarta] testing approach.

[source,bash]
----
mvn clean install                                  # All tests
mvn clean test -pl testsuite/integration/jsonrpc   # JSON-RPC only
mvn clean test -pl testsuite/integration/grpc      # gRPC only
mvn clean test -pl testsuite/integration/rest      # RESTful HTTP/JSON only
----

The `jsonrpc` and `rest` modules each provision *two* servers and run their suite against both:

* `target/wildfly-layers` from the hardcoded layer list, and
* `target/wildfly-glow` from the layer set WildFly.

Glow discovers by scanning the Arquillian deployment.
Both run automatically via `mvn clean install`.
Results are differentiated by the `-layers` and `-glow` suffixes on the surefire reports.

The `grpc` module provisions only the hardcoded server: it additionally requires the gRPC feature-pack
and its `grpc` layer, which no A2A layer depends on and which Glow cannot infer from a deployment - see
<<Choosing Server Transport with Glow>>.

== Running the TCK

The feature-pack includes a TCK (Technology Compatibility Kit) module that runs the official A2A protocol TCK against WildFly.

=== Prerequisites

* Java 17 (or newer)
* Maven 3.9 (or newer)
* Python 3.11 (or newer) with `uv` package manager

=== Build and Run TCK

. Build the feature-pack:

[source,bash]
----
mvn clean install
----

. Build and provision the TCK server:

[source,bash]
----
mvn package -pl tck -am
----

. Start the WildFly server:

[source,bash]
----
SUT_HOST=localhost:8080 SUT_GRPC_HOST=localhost:9555 tck/target/wildfly/bin/standalone.sh --stability=experimental
----

. Clone and set up the A2A TCK:

[source,bash]
----
git clone https://github.com/a2aproject/a2a-tck.git
cd a2a-tck
git checkout 1.0.0.alpha2
pip install uv
uv pip install -e .
----

. Run the TCK:

[source,bash]
----
uv run ./run_tck.py --sut-host http://localhost:8080 -v
----

. Stop the server:

[source,bash]
----
mvn wildfly:shutdown -pl tck
----

TCK Endpoints Reference

* JSON-RPC: `http://localhost:8080`
* REST (HTTP-JSON): `http://localhost:8080`
* gRPC: `localhost:9555` (gRPC endpoint provisioned by the FP runs on separate Netty-backed port)
